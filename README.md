# Мини-CRM «Объекты и задачи»

CRM для строительной компании. Постановщики управляют объектами и задачами, исполнители выполняют назначенную работу и отправляют её на проверку.

Стек — React, TypeScript, Supabase, TanStack Router и Query, shadcn/ui. [Репозиторий на GitHub](https://github.com/montanaaq/miniCRM).

## Локальный запуск

Понадобятся Node.js 24 и [Vite+](https://viteplus.dev/guide/).

```sh
vp install
cp .env.example .env.local
```

Укажите в `.env.local` URL проекта Supabase и публичный ключ. Используйте только эти переменные во фронтенде. Пароль базы и ключи `service_role` / `sb_secret_*` храните вне репозитория и сборки.

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your_public_key
```

```sh
vp run dev
```

## База и демоданные

1. В настройках Supabase включите Data API и провайдер Email. Отключите открытую регистрацию и анонимный вход.
2. Примените [миграции](supabase/migrations) в порядке имён файлов через SQL Editor или Supabase CLI. В существующей базе применяйте только пропущенные миграции, включая [проверку комментариев](supabase/migrations/202611060002_reject_blank_revision_comments.sql). Клиент ожидает поля `version` из миграции `202611060001_record_versions.sql`.
3. В **Authentication → Users** создайте пользователей из таблицы, задайте указанные демопароли и включите **Auto Confirm User**.
4. Выполните [seed.sql](supabase/seed.sql). Он назначит роли и создаст 3 объекта и 6 задач во всех пяти статусах. Повторный запуск не дублирует записи и сохраняет существующие правки.

| Роль          | Email                    | Пароль               |
| ------------- | ------------------------ | -------------------- |
| Постановщик   | `manager@minicrm.test`   | `managermanager`     |
| Исполнитель 1 | `executor1@minicrm.test` | `executor1executor1` |
| Исполнитель 2 | `executor2@minicrm.test` | `executor2executor2` |

Эти пароли предназначены для тестовых аккаунтов на демостенде. Для сдачи отправьте пары email и пароль работодателю в чате по отклику.

## Как работает CRM

Постановщик добавляет стройку с названием и адресом, создаёт задачи и назначает ответственных. На странице объекта видны его задачи и их этапы. Исполнитель входит со своим email и паролем, открывает «Мои задачи» и видит только назначенную ему работу и связанные с ней стройки.

Исполнитель берёт задачу в работу и отправляет результат на проверку. Постановщик принимает его или возвращает задачу с пояснением, что исправить. После доработки исполнитель снова отправляет результат на проверку. В карточке обе роли видят, кто и когда изменил статус, с какого этапа на какой и с каким комментарием.

База данных проверяет, кому принадлежит задача и какое действие сейчас разрешено. Даже через прямой запрос исполнитель не может прочитать чужую задачу на общем объекте, изменить её, назначить себе другую роль или принять собственную работу. Историю записывает сама база, а пользователи приложения могут её только читать в доступных им задачах. Учётные записи создаёт администратор.

## Правила доступа и переходов

| Переход                         | Кто выполняет                       |
| ------------------------------- | ----------------------------------- |
| Создание → Новая                | Постановщик                         |
| Новая / На доработке → В работе | Назначенный исполнитель             |
| В работе → На проверке          | Назначенный исполнитель             |
| На проверке → Принята           | Постановщик                         |
| На проверке → На доработке      | Постановщик с непустым комментарием |

RLS ограничивает чтение и запись на всех четырёх таблицах. Права на столбцы закрывают прямое изменение статуса, автора и даты создания. Серверная функция `change_task_status` блокирует строку задачи, проверяет роль, назначение и ожидаемый статус, и отклоняет возврат с комментарием из одних пробельных символов. Затем сохраняет переход вместе с записью истории в одной транзакции.

## Решения и допущения

- У пользователя одна роль. Все постановщики работают с общим списком. Переназначение задачи сохраняет статус и автора, а доступ получает новый исполнитель.
- Создание задачи записывается в историю как переход в «Новую». История описывает изменения статуса. Редактирование текста и переназначение в неё не входят.
- Удаление мягкое. Записи уходят из рабочих списков, история сохраняется. Объект можно удалить после удаления всех его активных задач. Интерфейса восстановления нет.
- Версии записей защищают открытые формы от перезаписи более свежих правок. Даты отображаются в часовом поясе устройства.
- Статус можно изменить кнопкой или переносом на доске. Оба действия проходят одну серверную проверку. Рабочие списки загружаются целиком в пределах лимита Data API, пагинация для демо не реализована.

## Проверки и публикация

```sh
vp check
vp test
vp run build
```

Для проверки политик доступа примените миграции на отдельной тестовой базе с ролями и схемой Auth Supabase, затем запустите сценарии. Тестовые записи откатываются транзакцией.

```sh
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/security.sql
```

Для Vercel или Netlify используйте Node.js 24, `pnpm install --frozen-lockfile`, команду сборки `pnpm run build` и каталог `dist`. Задайте обе переменные `VITE_*` до сборки. Правила для прямых ссылок уже есть в [vercel.json](vercel.json) и [public/_redirects](public/_redirects). На другом хостинге настройте выдачу `index.html` для клиентских маршрутов.

## Что осталось перед сдачей

1. Сверить облачную базу с инструкцией выше. Проверить, что применены миграции, отключена регистрация и доступны три тестовые учётные записи с демоданными.
2. Опубликовать приложение, проверить вход под всеми тремя учётными записями, прямые ссылки, запрет чтения чужой задачи на общем объекте и полный цикл с возвратом на доработку и приёмкой. Отдельно проверить, что история видна после обновления страницы.
3. Запушить итоговый код и дать работодателю доступ к репозиторию. Отправить одним сообщением на hh.ru ссылку на опубликованное приложение, три пары email/пароль, ссылку на репозиторий и ссылки на разделы «Как работает CRM» и «Решения и допущения» этого README.
